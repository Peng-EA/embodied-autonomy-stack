# ADR-0003: 四条基线的定义与"各自关掉什么"

- 状态：已接受（**含已知不公平**，见 §后果） · 修订 2026-11-05（加入 `full` 配置）
- 日期：2026-11-05

## 背景

项目主张"LLM 不该做实时中心"。这种主张最容易变成自说自话：挑一个最差的对照组，赢一次，然后宣布成立。

所以必须把对照组**写死成可执行的配置**，并且公开承认每一组的弱点。
否则每次讨论都会回到"你的对照不公平"。

## 决策

**四条基线（B0 / B0′ / B1 / B2）都是消融版本**，配置在 [`evals/baselines/`](../../evals/baselines/)，
由 `sim/baseline.py` 读取（单一事实源，改 yaml 立即生效）。

另有一个**不属于基线**的配置 `full`：什么也不关，代表本系统的主张。
它没有 yaml，定义在 `sim/baseline.py`（否则又变成两处维护）。

| 配置 | 关掉什么 | 用途 |
|---|---|---|
| **`full`** | 什么都不关 | 本系统；与被消融的版本比较 |
| **B0** | L1/L2/L3 全关，决策全经 LLM | "LLM 中心"的极端形态 |
| **B0′** | 不依赖 LLM，改由脚本航点驱动 | 工业界现状的近似 |
| **B1** | 关情绪对行为的调制（L3 仍算） | 检验情绪是否只是装饰 |
| **B2** | 关 L1 抢占（需求照常生成） | 检验抢占权是否必要 |

正确的对照关系：

- `full` vs **B1** → 情绪调制的作用
- `full` vs **B2** → 抢占的作用
- `full` vs **B0′ / B0** → 结构差异

> 修订记录：首版把"B1"当成全开，导致标着 B1 的数据其实是 `full`。
> 引入 `full` 之后标签才和 yaml 一致（`b1-no-affect.yaml` 里 L3 = `enabled_but_not_modulating`）。

## 后果

### 正面

- 对照组可执行、可复现、可被第三方复跑；yaml 是唯一事实源。
- 每加一个机制，都能回答"关掉它会发生什么"。

### 负面（必须写清楚）

1. **B0 是稻草人**：关掉 L1 后它"没有需求来源"，自然不去充电。
   更公平的 B0 应该允许 LLM 读电池状态、自己决定去充电——那它可能表现不错。
   **在做这个更公平版本之前，B0 的差距不能当成"LLM 不行"的证据。**
2. **B0′ 只有行为树的外形**：是脚本化航点，不读电量、不做状态机，能力被严重低估。
3. **`full` vs B1 差异极小**（30.5% vs 30.8%）：说明当前场景里情绪调制几乎不影响结果，
   "情绪有用"目前**没有**被这批数据支持。
4. **每组只跑一次、单障碍物、参数刚标定**：只能算方向性证据，报不出显著性。

## 被否掉的方案

| 方案 | 否掉原因 |
|---|---|
| 只做 B0 vs full | 无法回答"是不是随便加个分层都行" |
| 用公开 benchmark 当对照 | 本项目是架构提案，不是 benchmark 选手 |
| 用论文里的数字当对照 | 不可复现；平台不同，比了也没意义 |
| 把 `full` 也写成 yaml | 会让"基线"和"本系统"混为一谈，且 yaml 里全是 enabled，没有信息量 |

- 2026-11-05：首版。
- 2026-11-05（同日）：引入 `full` 配置；纠正"B1 = 全开"的错误标签。
- 2026-11-06（缺陷复核）：确认 B0 的"不充电"不只是"没有需求来源"，而是 `sim/main.py` 里
  `l1.battery = max(30.0, ...)` 把电量钉死在 30.0%——**它连"没电"都不可能**。
  该行为随 v0.1.0 一起冻结（不改历史数字），档案与复现见 [`evals/v0.1-frozen/`](../../evals/v0.1-frozen/README.md)。
  公平版 B0（`b0f`）在 v0.2 的 `testbed/` 里重做。
