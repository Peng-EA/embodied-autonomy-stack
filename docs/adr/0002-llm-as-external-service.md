# ADR-0002: LLM 是 L4 调用的外部异步服务，不是 L4 本身

- 状态：已接受
- 日期：2026-11-05

## 背景

把 LLM 放进四层架构时，最自然的写法是"L4 = LLM"：规划就是让模型想，想完就执行。
这个写法在 demo 里很顺手，但它把三个工程约束藏了起来：

1. **延迟不可控**：模型响应是长尾分布（重试、限流、排队），而 L4 的时间尺度是 1–10 s+。
2. **会断线**：网络/额度/上游故障是常态，不是异常。
3. **会被替换**：今天的模型半年后就不在了，契约不能绑在某个供应商的接口上。

如果 LLM 就是 L4，这三件事就没有地方处理——系统要么卡住，要么整层失效。

## 决策

**L4 是规划协调器；LLM 是它调用的外部服务。**

- L4 负责：目标排序、任务分解、下发执行、**超时与降级**；
- LLM 只负责：语义规划与对话，输入 `semantic_plan_request`，输出 `semantic_plan_result`；
- 规划结果**永远是建议**：落地前必须过 L1/L2，随时可被抢占（见 [interfaces](../interfaces.md)）；
- LLM 不可用时，L4 必须有一条本地降级路径（`sim/` 里已实现并测过断线）。

## 后果

### 正面

- 断线不再等于停机：`--llm-disconnect` 注入后仍能走到充电桩（降级速度 ×0.85）。
- 模型可替换：换供应商只改 `MockLLMService`/适配层，L1–L3 与契约不动。
- 延迟变成显式参数（`timeout_ms`），而不是"希望它快"。

### 负面

- L4 变复杂了：要维护请求生命周期、超时、降级、重试策略。
- 多一次序列化/反序列化，语义细节可能在结构化时丢失（尤其长上下文）。
- "降级路径好不好"成了新的质量负担：降级太差，等于断线即失败。

## 被否掉的方案

| 方案 | 否掉原因 |
|---|---|
| L4 = LLM（直接调用） | 断线即停机；延迟无上界；契约绑死供应商 |
| LLM 只在"必要时"同步调用 | 同步调用会把 L1/L2 的实时性拖下水（哪怕只是偶尔） |
| 不要降级，断线就报错停机 | 与"机器人要能维持自己"的核心命题直接冲突 |
