# 架构决策记录（ADR）

> 状态：维护中

这里记录**已经做过的架构决策**，以及做它的理由和被接受的代价。
README 的「主张」是一句话结论；ADR 是那句结论为什么成立、以及在什么条件下会不成立。

## 什么时候写

写 ADR 的信号（满足任意一条就写）：

- 改了 `contracts/` 的语义（不是加可选字段那种）
- 改了 `evals/` 的基线定义（会让历史数据不可比）
- 在两个合理方案里做了取舍，且以后一定会有人问"为什么不用另一个"
- 修了一个**反复出现**的设计坑（例：抢占风暴、感知口径不一致）

不写：纯文字修订、补充说明、typo。

## 格式

```markdown
# ADR-000N: 一句话决策

- 状态：已接受 / 已废弃 / 被 ADR-XXXX 取代
- 日期：YYYY-MM-DD

## 背景
当时的约束与问题，要具体（哪个信号、哪份文档、哪个实验）。

## 决策
做了什么。一句话能说完最好。

## 后果
### 正面
### 负面（必须写，写不出负面就是没想清楚）

## 被否掉的方案
以及为什么否掉。

## 相关
代码 / 文档 / 实验 的链接
```

## 约定

1. ADR 一旦合并就不改内容；要改就写新的，把旧的标「被取代」。
2. 编号连续，不复用。
3. 每条 ADR 必须能回答：**如果这个决策是错的，我们会看到什么现象**。
